## ADR-001: Local-First Modular Desktop Architecture

**Status**: Accepted
**Owner**: Legacy/Inferred
**Viewpoint**: Functional, Deployment, Development

**Context**: MyBoTeam is split across a renderer, desktop shell, daemon, shared
core, and MCP tools, but ships as one desktop product.

**Evidence Found**: `pnpm-workspace.yaml`, `apps/web/package.json`,
`apps/desktop/package.json`, `packages/agent-core/package.json`, `AD.md`.

**Decision**: Use a local-first modular desktop architecture with separate
workspace boundaries for UI, shell, execution, shared core, and tools. Desktop
owns shell concerns: windows, tray, preload, packaging, updater, and OS
integrations. Daemon owns task execution, storage, secrets, provider settings,
connectors, token lifecycle, and long-lived background services. Desktop
connector code is limited to OS/browser/OAuth callback bridges required by the
shell.

**Consequences**: Clear ownership boundaries and no hosted backend for user
tasks or secrets. Packaging and tests must coordinate multiple build outputs and
cross-workspace contracts. Daemon and MCP assets are runtime-critical but
packaged separately from the UI.

**Common Alternatives**: A single Electron app would simplify packaging but
reduce execution isolation. A hosted backend would simplify background
processing but weaken local-first privacy.

**Confidence Level**: HIGH.

## ADR-002: Typed Renderer-to-Daemon Boundary

**Status**: Accepted
**Owner**: Legacy/Inferred
**Viewpoint**: Functional, Security, Development

**Context**: React does not call Node APIs directly. It uses a preload-exposed
`window.myboteam` API, which desktop handlers route toward daemon services.

**Evidence Found**: `apps/desktop/src/preload/index.ts`,
`apps/web/src/client/config/myboteam.ts`, `apps/web/src/client/stores/taskStore.ts`,
`packages/agent-core/src/daemon/client.ts`, `apps/daemon/src/daemon-routes-*.ts`.

**Decision**: Privileged operations are mediated through Electron preload and
typed daemon RPC instead of exposing Node, storage, or process execution to
React. All local process boundaries are treated as untrusted: every IPC/RPC
payload is validated before privileged work is performed. Shared TypeScript
types in `@myboteam/agent-core/common` and `@myboteam/agent-core/desktop-main`
are the authoritative cross-process contract; preload and web wrappers must
conform.

**Consequences**: The renderer stays behind a capability boundary and daemon
method types constrain contracts. UI features often require synchronized web,
preload, desktop, and daemon changes. Missing validation at any boundary is a
privilege escalation surface.

**Common Alternatives**: Direct Electron IPC from renderer would have fewer
layers and a weaker boundary. Renderer-to-daemon HTTP would be familiar but
create a broader local attack surface.

**Confidence Level**: HIGH.

## ADR-003: Detached Daemon With Local Socket JSON-RPC

**Status**: Accepted
**Owner**: Legacy/Inferred
**Viewpoint**: Concurrency, Operational, Deployment

**Context**: Desktop startup spawns a daemon and connects over a local socket.
The daemon owns task, storage, settings, provider, and event fan-out services.

**Evidence Found**:
`apps/desktop/src/main/daemon/daemon-connector-transport.ts`,
`packages/agent-core/src/daemon/socket-path.ts`,
`packages/agent-core/src/daemon/rpc-server.ts`,
`packages/agent-core/src/daemon/pid-lock.ts`, `apps/daemon/src/app-setup.ts`.

**Decision**: Background execution is isolated in a long-lived daemon process
connected to the desktop shell by local socket JSON-RPC. The daemon may remain
alive after all windows close when configured so background tasks can continue.
Daemon APIs must remain local-only; any HTTP endpoint requires authentication,
payload validation, and no exposure beyond localhost.

**Consequences**: Execution can outlive renderer reloads and avoids an HTTP port
for core RPC. Lifecycle, pid locks, stale sockets, reconnects, and logs add
operational complexity. Keep-alive behavior requires clear shutdown controls,
socket permissions, and stale process cleanup. Recovery is best-effort: desktop
reconnects to a live daemon, but active task recovery after daemon crash is not
guaranteed.

**Common Alternatives**: In-process Electron main services would be simpler but
less isolated. An HTTP daemon API would be easier to debug but broader in
exposure.

**Confidence Level**: HIGH.

## ADR-004: Per-Task OpenCode Server Runtimes

**Status**: Accepted
**Owner**: Legacy/Inferred
**Viewpoint**: Functional, Concurrency, Operational

**Context**: Task execution is delegated to OpenCode by starting local
`opencode serve` runtimes and driving them through the SDK.

**Evidence Found**: `apps/daemon/src/task-service.ts`,
`apps/daemon/src/opencode/server-lifecycle.ts`,
`apps/daemon/src/opencode/server-manager.ts`,
`packages/agent-core/src/opencode/config-generator.ts`,
`packages/agent-core/src/opencode/cli-platform.ts`.

**Decision**: Launch per-task OpenCode server runtimes instead of embedding
agent orchestration directly in daemon code. OpenCode stays pinned by default;
upgrades are avoided unless needed, and compatibility work is handled
case-by-case. Each active task must get its own OpenCode server runtime for
isolation, cancellation, and cleanup.

**Consequences**: This reuses OpenCode runtime/provider support and gives
per-task cleanup boundaries. Startup latency and cleanup are user-visible.
OpenCode upgrades can alter prompts, protocol behavior, or runtime assumptions,
so each upgrade needs explicit review of affected prompts, SDK contracts, daemon
behavior, and packaged runtime smoke coverage as appropriate.

**Common Alternatives**: SDK-only orchestration would provide more control but a
larger maintenance burden. A shared OpenCode server would lower startup cost but
is not allowed for active task execution because it weakens isolation and
cleanup guarantees.

**Confidence Level**: HIGH.

## ADR-005: sql.js Data Plus Encrypted File Secrets

**Status**: Accepted
**Owner**: Legacy/Inferred
**Viewpoint**: Information, Security

**Context**: Structured state is stored locally via sql.js while secrets are
stored separately in encrypted JSON.

**Evidence Found**: `packages/agent-core/package.json`,
`packages/agent-core/src/storage/migrations/index.ts`,
`packages/agent-core/src/factories/storage.ts`,
`packages/agent-core/src/internal/classes/SecureStorage.ts`,
`apps/desktop/src/main/store/secureStorage-api-keys.ts`.

**Decision**: Store relational app state in local sql.js storage with explicit
migrations and store credentials in machine-derived encrypted secure storage
accessed through daemon services. `sql.js` is a deliberate packaging and
portability choice: it avoids native SQLite binaries while keeping the database
runtime pure JS/WASM and easier to bundle cross-platform. Encrypted file storage
is the intended long-term design for provider API keys, OAuth tokens, and
connector tokens. Migrations must be bidirectional: schema changes require
executable `up` and `down` migration code, both covered by tests. This extends
the constitution's immutable migration-history rule.

**Consequences**: This preserves local-first data and separates state from
secrets. Encrypted files require an app-managed export/import flow for backup
and migration; sql.js persistence needs migration discipline. Encrypted file
storage must retain strict handling so decrypted values do not leak to UI, logs,
traces, or test fixtures.

**Common Alternatives**: OS keychain would provide stronger platform integration
with more platform variance. A native SQLite driver would improve large-data
performance but complicate packaging.

**Confidence Level**: HIGH.

## ADR-006: Bundled First-Party MCP Tool Families

**Status**: Accepted
**Owner**: Legacy/Inferred
**Viewpoint**: Functional, Deployment, Evolution

**Context**: MCP tools are nested packages under agent-core and split by family:
browser/dev tooling, Google Workspace, WhatsApp, and task helper/auth tools.
OpenCode config points to their bundled entrypoints.

**Evidence Found**: `packages/agent-core/mcp-tools/*/package.json`,
`packages/agent-core/src/opencode/generator-mcp.ts`,
`packages/agent-core/src/opencode/generator-mcp-tools.ts`,
`apps/desktop/package.json` `extraResources` and `build:mcp-tools:*` scripts.

**Decision**: Treat MCP tools as connector-family sub-systems while shipping
them with the desktop app and injecting them into each OpenCode runtime.

**Consequences**: Connector-family boundaries make tool ownership clear while
preserving built-in onboarding. Tool dependencies and build outputs remain
coupled to desktop packaging. Missing dist files or bundled Node.js paths must
fail packaged build validation and task startup rather than silently disabling
required first-party tools.

**Common Alternatives**: User-installed MCP servers would be more flexible but
worse for onboarding. Daemon-native tools would simplify packaging but weaken
modularity.

**Confidence Level**: HIGH.

## Quality Requirements

Security, performance, availability, evolution, internationalization, usability,
and development-resource perspectives are relevant based on secure storage,
preload boundaries, daemon lifecycle, task concurrency, workspace packages,
localized resources, tests, and CI.

Target observability is structured telemetry for major runtime boundaries:
daemon lifecycle, task state transitions, OpenCode runtime startup and exit, MCP
tool availability, provider auth failures, and storage migrations. Diagnostics
must not expose secrets. Scrubbed product analytics may be enabled by default,
while diagnostics, traces, and support bundles remain local unless the user opts
in.
