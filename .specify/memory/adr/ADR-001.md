## ADR-001: Layered Desktop Architecture with Unix Socket JSON-RPC

### Status

**Accepted**

### Date

2026-06-24

### Owner

User/AI collaboration

### Sub-System

System (Cross-cutting)

### Context

**Problem Statement:**
The AI Agent Harness has 7 distinct layers (Desktop Shell, Web UI, Background Daemon, Agent Runtime, MCP & Tools, LLM Layer, Data Layer) that must communicate securely and efficiently. The system must run entirely on the user's machine with no cloud dependencies, enabling a local-first privacy model.

**Forces:**
- Renderer process (Web UI) must have zero direct access to Node.js APIs, filesystem, or daemon sockets — this is a hard security boundary
- The background daemon must outlive the Electron shell (survive window close) for persistent agent execution
- Communication must be bidirectional — the daemon pushes task progress, permissions, and notifications to the UI
- Typed, validated payload boundaries at every process boundary prevent data corruption and injection
- The daemon manages agent processes, MCP servers, and LLM provider calls — all I/O happens here, never in the renderer

### Decision

**Decision:**
The system uses a strictly layered 4-link communication chain:

```
[React UI] → contextBridge IPC → [Electron Main] → Unix socket JSON-RPC → [Daemon]
```

Each link is a typed, validated boundary:
1. **React UI** → `window.myboteam.*` typed API (exposed via contextBridge)
2. **Preload** — sole bridge between web and native; uses `ipcRenderer.invoke`/`ipcRenderer.on`
3. **Electron Main** — receives IPC, forwards to daemon via JSON-RPC client
4. **Daemon** — JSON-RPC server on Unix domain socket, typed method dispatch, push notifications

**Rationale:**
- ContextBridge ensures renderer has no direct Node.js/filesystem/socket access
- Unix domain sockets use filesystem permissions for security instead of network firewalls
- JSON-RPC is a standard, lightweight protocol with typed method dispatch
- Bidirectional communication via the socket supports real-time event streaming
- The daemon is a detached child process that can outlive the Electron shell
- Exponential backoff reconnection (200ms → 5000ms) with 10 attempts before respawn

### Consequences

#### Positive
- Strong security boundary — renderer code cannot access Node.js or filesystem
- Daemon can run headlessly (survives window close)
- Typed contracts at each boundary prevent silent data corruption
- JSON-RPC is easy to debug with standard tools

#### Negative
- More complex than a single-process approach
- Serialization overhead at each boundary
- Need synchronization for daemon startup/shutdown lifecycle

#### Risks
- Risk: Unix socket path length limits on macOS — mitigated by using short relative paths in data directory
- Risk: Daemon crash orphans UI — mitigated by reconnection logic with automatic respawn
- Risk: Socket file permission mismatch after OS user change — mitigated by recreating socket file on permission check failure
- Risk: Daemon startup race condition with stale socket file — mitigated by PID lock file and stale socket cleanup on daemon boot

### Common Alternatives

#### Option A: HTTP REST on localhost
**Description:** Daemon exposes HTTP REST API on localhost:45740. UI calls it directly.
**Trade-offs:** Simpler to implement and debug with standard HTTP tools; requires explicit port management, does not provide built-in push notifications (requires polling or WebSocket addition), and the open port presents a distinct attack surface profile compared to filesystem-permission-based sockets.

#### Option B: Single Electron process (no daemon)
**Description:** All logic runs in the Electron main process or renderer via Node integration.
**Trade-offs:** Eliminates IPC complexity and serialization overhead; renderer has direct Node.js/filesystem access, does not survive window close, and shares a single process for UI and background work.
