## ADR-008: Human-in-the-Loop (HITL) & Security Architecture

### Status

**Accepted**

### Date

2026-06-24

### Owner

User/AI collaboration

### Sub-System

System (Cross-cutting)

### Context

**Problem Statement:**
The PRD requires human approval before sensitive actions (sending emails, approving payments, modifying calendar events with external attendees). The system must pause execution, notify the user, and resume only after explicit input. Additionally, MCP server execution must be sandboxed for security.

**Forces:**
- HITL must be built before agents (PRD requirement) — safety boundaries exist from day one
- MCP servers run external processes that could access the filesystem or network
- The local-first model means no cloud escalation — all HITL is desktop-native
- The user may not be at the computer when HITL is triggered — timeout behavior is needed
- App store compliance requires user-initiated actions only

**References:**
- PRD Feature 5: HITL requirements (REQ-019 through REQ-022)
- MyBotTeam v0.3.0: HITL via permission request events through IPC chain
- MyBotTeam v0.4.0: Filesystem permission system with allow/deny rules
- Odysseus: Internal tool token for agent loopback

### Decision

**Decision:**

**HITL Flow:**
1. Agent attempts sensitive action (sending email, modifying external data, exceeding retry limit)
2. Daemon detects the action matches a HITL rule
3. Daemon pauses the agent execution, emits `permission.asked` event
4. Event flows: Daemon → JSON-RPC → Electron Main → IPC → Web UI
5. Web UI shows desktop notification + prompt in chat:
   - Pending action description (what the agent wants to do)
   - Context (why it needs approval)
   - Options: Approve, Modify, Reject
6. User responds → flows back through chain → daemon resumes or cancels agent
7. If user does not respond within 5 minutes: auto-reject with "Timed out" logged

**HITL Triggers (default rules, configurable):**
- Sending email or message
- Creating/modifying calendar events with external attendees
- Filesystem writes outside `~/Documents/MyBotTeam/`
- Retry count >= max configurable iterations (default: 3)
- First-time MCP server execution (safety prompt)
- User-marked sensitive operations in settings

**MCP Sandbox Security:**
- Each MCP server runs as a separate child process (process-level isolation)
- Permission rules in `filesystem_access_rules` table:
  - `{decision: allow|deny, grantType: temporary|persistent, operation, path, expiresAt}`
  - Deny rules checked first; most specific path match wins
- Sensitive paths always blocked: `.ssh`, `.env`, `.gnupg`, `.gitconfig`, system directories
- MCP manifests validated before execution (check for dangerous permissions)
- MCP server process killed and permissions revoked on timeout

**App Store Compliance:**
- All agent actions are user-initiated — agents never execute autonomously at startup
- HITL prompt before any network-bound action (email, API calls)
- No background daemon operations without user consent

### Consequences

#### Positive
- Safety boundaries exist before agents — foundational infrastructure
- HITL ensures user stays in control of sensitive operations
- App store compliance through user-initiated design
- MCP sandbox prevents privilege escalation

#### Negative
- HITL adds latency to sensitive operations (waiting for user response)
- 5-minute timeout may be too short for some workflows
- MCP sandboxing adds ~100-200ms startup overhead per server

#### Risks
- Risk: User gets too many HITL prompts and becomes annoyed — mitigated by configurable triggers and persistent grant option
- Risk: MCP sandboxing bypass discovered — mitigated by defense in depth: process isolation + restricted FS + manifest validation

### Common Alternatives

#### Option A: No HITL (fully autonomous)
**Description:** Agents execute all actions without user approval.
**Trade-offs:** Eliminates approval latency for all agent actions; does not provide safety guardrails for sensitive operations and may not satisfy app store requirements for user-initiated actions.

#### Option B: Cloud-based HITL
**Description:** HITL prompts go to a cloud service for mobile notification.
**Trade-offs:** Enables mobile device approval workflows; requires cloud infrastructure, introduces network dependency, and transmits action metadata externally.
