## ADR-002: Eve Agent Harness for Agent Runtime

### Status

**Accepted**

### Date

2026-06-24

### Owner

User/AI collaboration

### Sub-System

Agent Runtime

### Context

**Problem Statement:**
The Agent Runtime must orchestrate specialized agents (Orchestrator, Secretary, Accountant) that execute user tasks via LLMs with tools. The runtime must support deterministic routing for common patterns, provider-agnostic LLM calls, and tool execution via MCP.

**Forces:**
- Agents need a deterministic, reproducible execution environment per agent type
- Common intents (filesystem, todo management) should bypass LLM entirely to prevent hallucination
- The runtime must support multiple agent types with different instructions, tools, and provider configs
- Tool execution must be sandboxed per agent (Secretary gets different tools than Accountant)
- The system must be extensible — adding a new agent type should not require core changes to the engine

**References:**
- Vercel Eve (https://eve.build) v0.12.0 — generates deterministic agent runtime files
- MyBotTeam v0.4.0 — uses Eve materializer to generate per-agent TypeScript projects on disk

### Decision

**Decision:**
Agent execution uses the **Eve Agent Harness** pattern:

1. **AgentDefinition** stored in SQLite: id, slug, name, role, description, instructions (system prompt), provider, model
2. **AgentMaterializer** generates deterministic Eve project files on disk at `.local-data/agents/{slug}/`:
   - `agent.ts` — `defineAgent()` configuration
   - `instructions.md` — system prompt + honesty policy + peer agent catalog
   - `tools/delegate_to_agent.ts` — delegation tool for orchestrator
   - `tools/mcp_{name}.ts` — one per assigned MCP server
3. Three routing tiers before dispatch (pre-dispatch, distinct from ADR-005 verification tiers):
   - **Tier 1** (deterministic): Filesystem intents → `FilesystemService` — regex-matched, zero LLM calls
   - **Tier 2** (deterministic): Todo/project intents → direct SQLite CRUD via `TodoService`
   - **Tier 3** (LLM): Everything else → Eve runtime calls provider with augmented instructions
4. Each agent can have different provider/model via per-agent override (see ADR-006)
5. Agent status lifecycle: `idle → materialized → starting → running → stopped → error`

**Rationale:**
- Deterministic (non-LLM) routing prevents hallucination for common patterns
- Eve file generation creates reproducible, inspectable agent definitions on disk
- Per-agent tool assignment via MCP allows granular access control
- Peer agent catalog injected into instructions enables orchestrator delegation without hardcoding
- SQLite as source of truth means agents survive restart without file regeneration every time

### Consequences

#### Positive
- Deterministic routing catches ~60% of common intents without LLM cost/latency
- On-disk agent files are debuggable and inspectable
- Adding a new agent = new SQLite record + materialize — no core code changes
- Each agent has isolated tool access based on MCP assignments

#### Negative
- Eve file generation adds ~50-100ms to agent startup
- Deterministic routing regex patterns must be maintained as intent patterns evolve
- On-disk files need invalidation when agent config changes

#### Risks
- Risk: Deterministic routing misses edge cases → falls through to LLM (graceful degradation)
- Risk: Eve version changes break file format — mitigated by pinning Eve version and testing materializer

### Common Alternatives

#### Option A: OpenCode SDK per-task processes
**Description:** Spawn `opencode serve` subprocess per task using `@opencode-ai/sdk/v2`.
**Trade-offs:** Provides a richer tool ecosystem and event streaming capabilities; introduces an external runtime dependency, has longer cold-start time, and requires additional configuration to control per-agent tool access.

#### Option B: Custom agent runtime (no Eve)
**Description:** Build a custom agent loop with provider API calls directly.
**Trade-offs:** Provides full control over agent lifecycle and execution; requires significant engineering investment to implement agent abstraction, tooling integration, and lifecycle management.
