## ADR-005: Verification Loop — Phase 1 (Foundation) 3-Tier + Phase 2 (Agent) CompletionEnforcer State Machine with User Override

### Status

**Accepted**

### Date

2026-06-24

### Owner

User/AI collaboration

### Sub-System

Agent Runtime

### Context

**Problem Statement:**
AI agents can hallucinate — fabricate file contents, claim success when an operation failed, or misunderstand user intent. The PRD requires >80% task pass rate and a verification loop built before agents. Additionally, PDR-009 establishes a CompletionEnforcer state machine that goes beyond basic pass/fail: detecting incomplete work, stalls, and partial completions, then attempting automatic continuation.

**Forces:**
- Some common intents (filesystem ops, todo CRUD) are fully deterministic — an LLM should never be involved
- The user must be able to override false negatives when the verification is wrong
- Tasks may be partially complete — the system should nudge agents to finish rather than failing
- Agents may stall or exit without calling `complete_task` — need stall detection and auto-continuation
- Verification must not add significant latency (>1s per check is too slow)
- Every verification result must be logged for audit and tuning
- The system must retry failed tasks before escalating to the user
- Max retry enforcement prevents infinite continuation loops (PDR-009: default 10 max)

**References:**
- MyBotTeam v0.4.0: 3-tier verification with deterministic routing + honesty policy + output sanitization
- Accomplish: CompletionEnforcer state machine with TaskInactivityWatchdog
- PRD: REQ-010 through REQ-014 (basic verification), REQ-044 through REQ-048 (CompletionEnforcer)
- PDR-009: System Agent Tools — CompletionEnforcer specification

### Decision

**Decision:**
Two-phase verification: a basic loop in Foundation milestone, superseded by the CompletionEnforcer in the Agent milestone.

**Phase 1 — Foundation Milestone: Basic 3-Tier Verification Loop**
Built as daemon middleware, executed before and after agent execution:

**Tier 1 — Pre-Dispatch Input Validation (before agent dispatch):**
- Regex-based intent classification against user message to gate LLM involvement
- Validates input is well-formed, permitted within workspace scope, and does not violate safety rules
- Feeds into ADR-002's dispatch routing (distinct concern: verification validates input, routing decides handler)
- Matched intents are verified and then dispatched via ADR-002 routing to direct services:
  - `FilesystemService` for read/write/list/directory operations
  - `TodoService` for create/list/complete project/todo operations
- Only verified intents proceed to LLM dispatch

**Tier 2 — LLM Augmentation (during agent execution):**
- Agent instructions are augmented with:
  - Honesty policy: "Never guess, never hallucinate tool results, never fabricate file contents"
  - Tool honesty: "If a tool returns an error, report the error. Never claim success."
  - Intent context: "The user's original request was: {original_message}"
- Injected into Eve agent's `instructions.md` at materialization time

**Tier 3 — Post-LLM Output Sanitization (after agent response):**
- Scan response for `<function_calls>` XML markup — strip if detected (hallucinated tool results)
- Scan for `tool_use_id` patterns — strip if detected
- Validate existence of tool call results before accepting claim

**Phase 2 — Agent Milestone: CompletionEnforcer State Machine**
Wraps the basic 3-tier loop with a state machine for automatic task recovery:

**States:**
- `IDLE` — task created, awaiting agent dispatch
- `EXECUTING` — agent running, monitored by TaskInactivityWatchdog
- `DONE` — agent called `complete_task(status=success)` AND all todos complete
- `PARTIAL_CONTINUATION_PENDING` — agent called `complete_task(status=success)` but todos remain incomplete → status downgraded to `'partial'`, continuation scheduled with nudge: "You reported success but N todos are still not complete"
- `CONTINUATION_PENDING` — agent process exited without calling `complete_task` → continuation scheduled with previous context
- `MAX_RETRIES_REACHED` — exceeded configurable max continuation attempts (default: 10) → task marked failed

**TaskInactivityWatchdog:**
- Monitors the SDK event stream during `EXECUTING`
- Soft timeout: 90s of no tool calls or message deltas → warning logged
- Hard timeout: 90s soft + 60s grace = 150s total → task marked failed
- Timeouts are configurable per task type

**Continuation Nudges:**
- Targeted prompts generated from incomplete work state
- Examples: "You completed 3/5 todos. Continue with the remaining 2." / "Your process exited unexpectedly. Resume where you left off."
- Prompts include the full conversation history — no loss of context

**User Override:**
- Every failed verification shows the original response and the failure reason in the UI
- User can click "Accept Anyway" to override and mark task as success
- Override patterns are logged to `debug_logs` with direction, source, content for tuning thresholds

**Retry Policy:**
- Foundation phase: configurable max iterations (default: 3), strict timeout per iteration (default: 60s), escalate to HITL at max
- Agent phase: CompletionEnforcer handles retries with state machine; max 10 continuations before MAX_RETRIES_REACHED
- Failed verifications at max iterations → escalate to HITL prompt

### Consequences

#### Positive
- ~60% of common intents bypass LLM entirely (zero latency, zero cost, zero hallucination risk)
- CompletionEnforcer recovers partial completions — target >90% task completion rate
- Inactivity detection prevents stalled agents from hanging indefinitely
- Continuation nudges salvage tasks that would have failed in basic verification
- User override prevents frustration from false negatives
- Override data enables continuous verification improvement

#### Negative
- Regex patterns for deterministic routing must be maintained
- Output sanitization may occasionally strip legitimate content (false positive)
- CompletionEnforcer state machine adds complexity to the task execution pipeline
- Continuation nudges consume additional LLM tokens (user pays via BYOK)
- User override logs require privacy-respecting telemetry to improve

#### Risks
- Risk: Regex patterns miss new intent patterns — mitigated by fallthrough to LLM (graceful degradation)
- Risk: Override patterns are too frequent (indicates poor verification) — mitigated by alerting on override rate >10%
- Risk: Continuation loops consume excessive tokens — mitigated by max retry count (10) and timeout enforcement
- Risk: False-positive inactivity detection (agent is thinking, not stalled) — mitigated by configurable timeouts per task type

### Common Alternatives

#### Option A: LLM-only verification
**Description:** Use a secondary LLM call to verify the primary agent's output.
**Trade-offs:** Simple to implement with a single verification pathway; doubles LLM cost and latency per verification, and the secondary LLM carries the same hallucination risk as the primary.

#### Option B: Deterministic routing only
**Description:** Only Tier 1, no LLM augmentation or sanitization.
**Trade-offs:** Provides lowest latency for deterministic intents; does not protect against LLM hallucinations for non-deterministic tasks and provides no output validation.

#### Option C: Simple fail-on-error (no CompletionEnforcer)
**Description:** Basic verification loop checks pass/fail once with no recovery.
**Trade-offs:** Simplest implementation within Foundation milestone scope; does not attempt task recovery for partial completions or stalled agents — addressed by CompletionEnforcer in Agent milestone.
