## ADR-009: Skill & Knowledge System

### Status

**Accepted**

### Date

2026-06-24

### Owner

User/AI collaboration

### Sub-System

Agent Runtime

### Context

**Problem Statement:**
Static system prompts limit what agents can learn and remember. Users need agents to acquire new capabilities from conversation, follow persistent preferences, and retain context across sessions. Three complementary mechanisms are needed: reusable skill creation, persistent memory, and standing instructions.

**Forces:**
- Agents should learn from conversation without requiring users to configure anything manually
- Skills must be safe — automatically creating executable content from LLM output carries security risk
- Memory must persist across sessions without manual user intervention
- Users should be able to set once, use forever preferences ("always sign with my full name")
- Memory must support both structured (categorized facts) and semantic (vector search) retrieval
- Skill creation must have rollback capability in case the generated skill is wrong
- Vector search (ChromaDB) is optional — the core system must work with SQLite only

**References:**
- OpenClaw: Skill Workshop with proposal lifecycle, SKILL.md format, security scanning
- OpenClaw: Standing Orders as workspace files loaded into every session
- Odysseus: Memory system with categorized entries, LLM extraction, consolidation
- PDR-007: Agent Skill & Knowledge System

### Decision

**Decision:**
Three-part Knowledge System:

**Part 1: Skill Workshop**
Skill creation via proposal lifecycle managed by the daemon:

**Skill Definition:**
- Stored as `SKILL.md` files with YAML frontmatter: `name`, `description`, `command`, `gating` rules (format owned by ADR-003)
- Source: `bundled-skills/` (read-only, shipped with app) and `{dataDir}/skills/` (user-created)
- Static discovery and injection into system prompt handled by ADR-003's pipeline
- This ADR extends with lifecycle management: creation, security scanning, rollback

**Proposal Lifecycle:**
1. `create` — user says "make a skill from what we just did" → daemon generates proposal from conversation context using LLM
2. `pending` — proposal stored in SQLite, user notified via UI
3. `apply` — on user approval, daemon writes `SKILL.md`, stores rollback metadata (previous version in SQLite)
4. `reject` — proposal discarded
5. `quarantine` — security scan flagged malicious content → isolated, user notified
6. `revise` — user requests changes → proposal sent back to LLM for modification

**Security Scanning:**
- Pre-apply scan of every proposal for: dangerous bash commands, network access, filesystem paths outside workspace, encoded payloads
- Scanned by a secondary LLM call with strict security criteria
- Flagged proposals go to `quarantine` instead of `pending`

**Rollback:**
- Before applying any skill change, daemon writes the previous version to SQLite `skill_versions` table
- Rollback restores the previous file content and removes the current version

**Part 2: Memory System**
Persistent categorized memory stored in SQLite with optional vector search:

**Memory Categories:**
- `facts` — general knowledge the agent learned
- `preferences` — user preferences ("I prefer dark mode")
- `identity` — user identity ("my name is Sarah")
- `events` — past events ("meeting with Client X on Tuesday")
- `contacts` — contact information
- `projects` — project context
- `instructions` — procedural instructions

**Extraction:**
- Background task runs after each conversation turn
- Sends conversation excerpt to LLM with extraction prompt
- LLM returns structured memory entries with category, content, and optional embedding
- Entries written to `memory_entries` table

**Consolidation:**
- Nightly background task scans for duplicate or stale entries
- Merges duplicate facts (same category + similar content)
- Removes entries older than configurable retention window

**Retrieval:**
- Primary: SQLite queries by category, keyword, or time range (<500ms)
- Optional: ChromaDB vector search for semantic retrieval (<2s) — gated by configuration
- Before each agent session, relevant memory entries are injected into the system prompt

**Part 3: Standing Orders**
Persistent agent instructions stored as workspace files:

- Created from natural language ("always sign emails with my full name")
- Stored as individual files in `{dataDir}/standing-orders/{slug}.md`
- Content: "Always [instruction]" format in markdown
- Loaded into every agent session's `instructions.md` at Eve materialization time
- Management UI: list, edit, pause, remove
- Ordering: applied in alphabetical file order (prefix with numbers for priority)

**Integration:**
- All three parts feed into the agent's materialized `instructions.md` at session start
- Skill Workshop produces `SKILL.md` files → injected as `<available_skills>`
- Memory System produces `memory.md` → injected as `<user_context>`
- Standing Orders produce `standing-orders.md` → prepended to system prompt

### Consequences

#### Positive
- Agents learn and improve over time — core retention driver
- Users can create reusable workflows without any configuration UI
- Standing orders eliminate repetitive instructions
- Memory enables context-aware agent behavior across sessions
- Security scanning prevents malicious skill injection
- Rollback makes skill creation safe to experiment with

#### Negative
- Skill Workshop requires LLM calls for proposal generation (costs user tokens)
- Memory extraction adds latency after each conversation turn
- Vector search (ChromaDB) is an optional dependency — must work without it
- Standing orders grow over time — need prompt budget management
- Security scanning can produce false positives, rejecting valid skills

#### Risks
- Risk: Security scanning false positives frustrate users — mitigated by manual override for quarantine
- Risk: Memory bloat degrades agent performance — mitigated by configurable limits, consolidation, user editing
- Risk: Users create too many standing orders consuming prompt budget — mitigated by ordering and max limit

### Common Alternatives

#### Option A: Skills only, no memory
**Description:** Skill Workshop and Standing Orders only, defer Memory System to post-MVP.
**Trade-offs:** Simpler implementation but agents lose factual recall — users repeat context each session.

#### Option B: Memory only, no skills
**Description:** Memory System only, no Skill Workshop or Standing Orders.
**Trade-offs:** Agents remember facts but cannot learn new procedures — miss the key differentiator.
