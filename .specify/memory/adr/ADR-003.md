## ADR-003: MCP & Skills Tool Organization

### Status

**Accepted**

### Date

2026-06-24

### Owner

User/AI collaboration

### Sub-System

MCP & Tools

### Context

**Problem Statement:**
Agents need tools to execute user tasks — reading files, accessing email, managing calendars, browsing the web. Tools must be organized so that some are available to all agents (shared), some are agent-specific (Secretary gets email, Accountant gets invoice tools), and advanced users can add custom tools.

**Forces:**
- The Model Context Protocol (MCP) is the standard for tool extensibility — it must be the primary mechanism for external tools
- Frequently-used core tools (file read/write, search) need sub-500ms latency — MCP stdio overhead is too slow for these
- Safety-critical tools (file confinement, secret storage) should run in-process where they can enforce policy without cross-process trust issues
- Some tools are lightweight utility functions that don't need MCP process overhead
- Skills (markdown instructions) complement tools by teaching agents how to use tools effectively
- Tool access must be granular — each agent gets only the tools it needs
- PDR-006 establishes that workspace-confined file tools are foundation infrastructure, not MCP concerns

**References:**
- Accomplish: 17 standalone MCP server packages + skills system with YAML frontmatter
- OpenClaw: 58 bundled skills, skill discovery pipeline with SKILL.md files
- MyBotTeam v0.4.0: Eve tool stubs generated per agent

### Decision

**Decision:**
Three-tier tool organization:

**Tier 1: Daemon-Native Tool Suite** (apps/daemon/src/services/)
- Built-in tools that run directly in the daemon process — no MCP overhead
- Used for core operations where latency and tight integration matter:
  - `read` — partial file reads with offset/limit, returns content with line numbers
  - `write` — creates parent directories, returns unified diff of changes
  - `edit` — FIND/REPLACE string replacement with uniqueness checking and `replace_all` flag; fails atomically on non-unique match
  - `ls` — list directory contents with optional include/exclude patterns
  - `glob` — pattern-based file search respecting `.gitignore`-style patterns
  - `grep` — content search across files, skips binary files
  - `complete-task` — Signal task completion status to daemon (internal stub; external MCP variant available for plugin consumers)
  - `request-connector-auth` — Initiate connector OAuth flow (internal stub; external MCP variant available for plugin consumers)
- All file tools confined to a configurable workspace root directory (safety boundary)
- File operations return unified diffs for auditability
- Exposed to agents as Eve tool stubs at materialization time, executing against daemon's internal services

**Tier 2: Bundled MCP Servers** (packages/mcp-servers/)
- Standalone MCP server packages, each using `@modelcontextprotocol/sdk` with `StdioServerTransport`
- Built via tsup → output `dist/index.mjs`
- Registered in Eve agent's generated `tools/` directory at materialization time
- Organized by category:
  - `filesystem/` — read, write, list, copy, move, delete (permission-scoped)
  - `gmail-mcp/` — Gmail read/send (requires Google OAuth)
  - `calendar-mcp/` — Google Calendar management
  - `gws-mcp/` — Google Workspace (Sheets, Docs)
  - `complete-task/` — External MCP-server variant for plugin consumers (agents use daemon-native stub by default)
  - `request-connector-auth/` — External MCP-server variant for plugin consumers (agents use daemon-native stub by default)

**Tier 3: Eve Tool Stubs** (generated per agent via materializer)
- Lightweight TypeScript functions in `agent/tools/` directory
- Used for utility operations that don't need external process: `get_local_time`, simple calculations
- Defined via Eve's `defineTool` from `eve/tools`

**Skills System (Static Pipeline)** (bundled-skills/)
- Defines the SKILL.md file format: markdown with YAML frontmatter (`name`, `description`, `command`, `gating`)
- Discovered via pipeline: scan `bundled-skills/` and `{dataDir}/skills/` directories → parse frontmatter → reconcile with SQLite → inject into agent system prompt as `<available_skills>` XML block
- Static format and injection only — full lifecycle management (creation, security scanning, rollback) owned by ADR-009

**Tool Assignment Model:**
- Join table `agent_mcp_assignments`: which MCP servers each agent can access
- Global MCP servers available to all agents
- Tool classification in daemon: `NON_TASK_CONTINUATION_TOOLS` (todowrite, complete_task, etc.) don't count as continuation

**MCP Server Lifecycle:**
- Daemon spawns MCP servers as child processes via stdio transport
- Each server runs in its own process with restricted filesystem access
- OAuth tokens refreshed automatically during config generation

### Consequences

#### Positive
- Daemon-native tools have sub-500ms latency (no IPC overhead)
- File confinement enforced in-process — no cross-process trust needed
- Process isolation for MCP servers — MCP servers can't access each other's data
- Skills as markdown files are easy to author, version, and share
- Eve stubs handle simple tools without MCP overhead
- Tool assignment granularity supports per-agent access control
- User can add custom MCP servers via settings UI

#### Negative
- Three tiers add complexity — need clear criteria for which tier a tool belongs to
- Daemon-native tools must be carefully coded (can crash daemon if buggy)
- OAuth token refresh must be handled for Google Workspace tools
- MCP server startup adds ~200-500ms per tool on first use

#### Risks
- Risk: MCP sandboxing bypass — mitigated by process-level isolation, restricted filesystem, manifest validation
- Risk: OAuth token expiry breaks tool mid-task — mitigated by automatic refresh in config generation
- Risk: Daemon-native tool crash propagates to daemon process — mitigated by input validation, try-catch boundaries, and daemon watchdog restart
- Risk: MCP server memory leak affects daemon — mitigated by per-server process isolation and daemon-level resource monitoring

### Common Alternatives

#### Option A: All tools as MCP servers
**Description:** Every tool including file operations runs as an external MCP server process.
**Trade-offs:** Provides uniform process isolation across all tools; adds 200-500ms latency per file operation due to IPC overhead, which affects core workflows.

#### Option B: All tools in daemon process
**Description:** No MCP at all — every tool runs in-process.
**Trade-offs:** Eliminates IPC overhead for fastest execution; does not provide process isolation between tools, meaning a misbehaving tool affects the entire daemon process.
