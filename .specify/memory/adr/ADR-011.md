## ADR-011: Testing Strategy — Multi-Layer Test Architecture for Monorepo

### Status

**Accepted**

### Date

2026-06-24

### Owner

User/AI collaboration

### Sub-System

System (Cross-cutting)

### Context

**Problem Statement:**
The constitution (§II) requires test-first quality: automated tests before or alongside implementation, RED phase before implementation, contract and integration tests at boundaries. Across 10 ADRs covering 7 architectural layers, no ADR documents how its decision will be tested. A unified testing strategy is needed that covers all layers while respecting the monorepo structure.

**Forces:**
- Each layer has different test requirements: Web UI (component/accessibility), Desktop (integration IPC), Daemon (service/integration), Agent Runtime (simulation), MCP servers (contract), Storage (migration/data integrity)
- Cross-process type contracts must be tested at every boundary — a type change in agent-core should fail tests in web, daemon, and desktop
- The daemon is the most critical system — test coverage must be highest here
- MCP servers run as external processes — testing requires spawning child processes
- Storage migrations must be tested bidirectionally (up + down) for safe rollbacks
- The CompletionEnforcer state machine must be tested exhaustively (all states, all transitions)
- E2E tests should validate the full chain but be kept minimal to avoid brittleness

**References:**
- Constitution §II: Test-First Quality — RED phase, contract/integration/unit organization
- ADR-004: Storage migrations must be tested bidirectionally
- ADR-005: CompletionEnforcer state machine needs exhaustive state transition tests
- ADR-007: Monorepo structure determines test location and dependency order

### Decision

**Decision:**
Five-layer test architecture, organized by isolation level:

```
tests/
├── unit/                    — Single module/class/function tests
│   ├── agent-core/          — Storage, providers, types, services
│   ├── daemon/              — RPC routes, services
│   ├── web/                 — Components, stores, hooks
│   ├── desktop/             — Main/preload process logic
│   └── mcp-servers/         — Per-server unit tests
├── contract/                — Cross-process type boundary tests
│   ├── types/               — Common type contracts (JSON-RPC payloads, events)
│   └── api/                 — RPC method signatures, event payloads
├── integration/             — Multi-module tests with real dependencies
│   ├── daemon/              — Service integration (FilesystemService + TodoService)
│   ├── daemon-mcp/          — Daemon talking to MCP server processes
│   ├── ipc/                 — Full IPC chain (React → preload → main → daemon)
│   ├── storage/             — SQLite migrations up + down, vault operations
│   └── agent/               — Agent materialization + runtime lifecycle
├── simulation/              — Agent task simulation tests
│   ├── verification/        — Verification loop rules, CompletionEnforcer state machine (exhaustive)
│   ├── routing/             — Deterministic routing regex patterns
│   └── agents/              — Agent behavior with mock LLM provider
└── e2e/                     — Full chain tests (minimal, critical paths only)
    ├── happy-path/          — File read/write → agent response → UI display
    ├── hitl/                — Permission request → approve/reject/timeout
    └── recovery/            — Daemon restart, agent crash recovery
```

**Test Framework & Tooling:**
- Vitest as the primary test runner (unified config in `vitest.workspace.ts`)
- Playwright for web UI component tests and E2E
- `supertest`-style HTTP testing for JSON-RPC (daemon)
- in-memory SQLite for storage unit tests (separate from production database)
- Mock LLM provider for agent simulation tests (returns canned responses)

**Per-Layer Testing Requirements:**

**agent-core (shared contracts, storage, providers):**
- Unit: 90%+ line coverage for storage, vault, type validation
- Contract: TypeScript compile-time type checking across dependent packages
- Integration: Migration tests (up then down, verify schema at each step)
- Storage tests use in-memory SQLite — never touch production `.local-data/myboteam.db`

**daemon (RPC routes, services, task execution):**
- Unit: 85%+ line coverage for service logic, RPC handlers
- Integration: Full-service tests with real SQLite (temporary database per test)
- Integration: MCP server spawn/kill lifecycle tests
- Simulation: Verification loop rules tested exhaustively (all 3 tiers, all 6 CompletionEnforcer states)

**desktop (Electron main, preload):**
- Integration: IPC chain test — mock daemon socket, verify contextBridge API contract
- Unit: Preload script tests with mocked `contextBridge`

**web (React UI):**
- Unit: Component rendering, store logic, hook tests with Vitest + testing-library
- Integration: Page-level tests with mocked daemon RPC responses
- E2E: Playwright tests for critical flows (limited to 5 test files max)

**mcp-servers (bundled MCP packages):**
- Unit: Per-server unit tests
- Contract: MCP protocol compliance tests (validate tool definitions, call format, response format)
- Integration: Server process spawn, tool call, response handling

**CompletionEnforcer State Machine Testing:**
- Exhaustive state transition coverage:
  - `IDLE → EXECUTING → DONE` (success path)
  - `IDLE → EXECUTING → PARTIAL_CONTINUATION_PENDING → EXECUTING → DONE` (nudge recovery)
  - `IDLE → EXECUTING → CONTINUATION_PENDING → EXECUTING → DONE` (stall recovery)
  - `IDLE → EXECUTING → PARTIAL_CONTINUATION_PENDING → MAX_RETRIES_REACHED` (exhaustion)
  - `IDLE → EXECUTING → MAX_RETRIES_REACHED` (hard timeout)
- TaskInactivityWatchdog: soft timeout → warning, hard timeout → fail, configurable thresholds
- Continuation nudge generation: verify prompt content references incomplete work

**Constitution Compliance:**
- RED phase: Tests written before implementation, verified failing on first run
- Contract tests: All cross-package type boundaries tested
- Integration tests: All IPC, daemon-MCP, daemon-storage boundaries tested
- Quality gate: All tests must pass before merge (enforced by CI)

### Consequences

#### Positive
- Clear testing ownership per monorepo package
- Migration tests prevent silent data corruption
- CompletionEnforcer exhaustive tests prevent task lifecycle bugs
- Separation of unit/integration/simulation/E2E prevents brittle test suites
- Mock LLM provider enables deterministic agent testing without API costs

#### Negative
- Simulation and E2E tests increase CI pipeline time
- Maintaining mock LLM provider responses requires ongoing effort as agent behavior changes
- Storage tests with in-memory SQLite may miss WAL-mode-specific issues

#### Risks
- Risk: E2E tests become brittle and flaky — mitigated by strict limit (max 5 test files) and critical-path-only scope
- Risk: Mock LLM provider diverges from real LLM behavior — mitigated by periodic smoke tests with real provider
- Risk: Migration tests become stale — mitigated by requiring migration tests in code review checklist

### Common Alternatives

#### Option A: No centralized test strategy
**Description:** Each package defines its own test approach independently.
**Trade-offs:** Flexible but inconsistent coverage, no cross-boundary contract testing, hard to enforce constitution compliance.

#### Option B: E2E-only testing
**Description:** Test only through the full application chain.
**Trade-offs:** Covers real user scenarios but slow, brittle, and doesn't isolate which layer failed. Poor for TDD workflows.
