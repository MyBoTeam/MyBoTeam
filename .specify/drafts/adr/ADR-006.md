## ADR-006: LLM Provider Model — Hybrid Global Default with Per-Agent Override

### Status

**Accepted**

### Date

2026-06-24

### Owner

User/AI collaboration

### Sub-System

LLM Layer

### Context

**Problem Statement:**
Users bring their own LLM API keys (BYOK) via supported providers. The system must support multiple providers (OpenAI, Anthropic, local LLMs) and multiple models per provider. Different agents may benefit from different models — the Orchestrator might use Claude for reasoning, while the Accountant uses GPT-4 for structured data.

**Forces:**
- BYOK model means zero infrastructure cost but user must configure at least one provider
- Local LLM support is required for absolute privacy (REQ-002)
- API keys must be stored securely in the OS keychain (REQ-004)
- The target persona (solopreneur) wants simplicity — one provider setup, not a complex config
- Provider API changes must not break agent functionality — abstraction layer is needed

**References:**
- MyBotTeam v0.4.0: Per-agent provider config with ProviderClient abstraction
- PRD Feature 1: BYOK & LLM Connectivity requirements

### Decision

**Decision:**
Hybrid provider model:

**Global Default Provider:**
- One default provider + model configured at the application level
- Used by all agents unless explicitly overridden
- Set during onboarding (first-run wizard)
- Allows switching between cloud providers and local LLM

**Per-Agent Override:**
- Each agent definition in SQLite has optional `provider` and `model` fields
- If set, overrides the global default for that agent only
- Stored in `agents` table as nullable fields

**Provider Abstraction Layer:**
- `ProviderClient` interface in `packages/agent-core/providers.ts`
- Supports Anthropic (Claude) and OpenAI (GPT) as first-class providers
- Extensible interface for future providers (Bedrock, Vertex, Ollama, LMStudio)
- All provider calls go through this abstraction — no direct provider SDK calls in agent logic
- Local LLM support via OpenAI-compatible API endpoint (Ollama, llama.cpp, LM Studio)

**Secret Storage:**
- API keys encrypted at rest in `secure-storage.json` (AES-256-GCM)
- Keys stored per provider, not per agent
- Decrypted keys injected into Eve provider config at materialization time
- Keys never enter the renderer process

**Provider Configuration Flow:**
1. User enters API key via UI settings
2. Daemon receives key via RPC, encrypts it into vault
3. On agent materialization, Eve config is generated with decrypted key (in memory only)
4. Provider calls are made directly from the user's machine — no proxy

### Consequences

#### Positive
- Simple default case: one provider setup, all agents use it
- Flexible override: power users can optimize agent-model fit
- Provider abstraction insulates from API changes
- Local LLM option for absolute privacy

#### Negative
- Per-agent override adds UI complexity (need to show in settings)
- Provider abstraction adds indirection for provider-specific features
- Local LLM setup may be complex for non-technical users

#### Risks
- Risk: Provider API changes break abstraction — mitigated by contained adapter layer, tested per integration
- Risk: User switches provider mid-session — mitigated by in-memory provider config cached per agent materialization

### Common Alternatives

#### Option A: Single global provider (no per-agent config)
**Description:** All agents use the same provider/model. Simple.
**Trade-offs:** No optimization flexibility but significantly simpler UX. Best for the target persona.

#### Option B: Full per-agent provider config (no global default)
**Description:** Every agent must be configured independently.
**Trade-offs:** Maximum flexibility but terrible UX — solopreneur should not configure 3 different API keys.

### Constitution Alignment

| Principle | Alignment | Notes |
|-----------|-----------|-------|
| Security | ✅ Compliant | Keys encrypted at rest, never in logs/renderer |
| Simplicity | ✅ Compliant | Global default covers simple case |
| Human Oversight | ✅ Compliant | User controls which provider/model each agent uses |
