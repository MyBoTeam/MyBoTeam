## ADR-007: Monorepo Structure — pnpm Workspace with 3 Apps + Shared Packages + Skills

### Status

**Accepted**

### Date

2026-06-24

### Owner

User/AI collaboration

### Sub-System

System (Cross-cutting)

### Context

**Problem Statement:**
The project has 7 architectural layers that need clear ownership boundaries, independent testability, and separate build pipelines. The monorepo structure must support sharing types between layers while preventing cross-boundary dependencies.

**Forces:**
- Each layer has different build targets: Vite (web), tsup (daemon), tsc (shared packages), electron-builder (desktop)
- Shared type contracts must be the single source of truth across process boundaries
- MCP servers are independent packages with their own dependencies and build configuration
- Skills are markdown files that don't need compilation but must be discoverable at runtime
- v0.3.0 established a proven 3-app + agent-core structure that should be reused
- The project must support both workspace dev (pnpm --filter) and independent package development

### Decision

**Decision:**

```
myboteam_v0.5.0/
├── apps/
│   ├── web/             @myboteam/web       — React UI (Vite + React Router + Zustand)
│   │   ├── src/                              — Routes, pages, stores, components, i18n
│   │   └── package.json                      — Vite build, React dependencies
│   ├── desktop/         @myboteam/desktop    — Electron shell (main + preload)
│   │   ├── src/main/                         — Electron main process
│   │   ├── src/preload/                      — contextBridge bridge
│   │   └── package.json                      — electron-builder config
│   └── daemon/          @myboteam/daemon     — Background daemon (Node.js)
│       ├── src/                              — RPC routes, services, task execution
│       └── package.json                      — tsup build, daemon dependencies
├── packages/
│   ├── agent-core/      @myboteam/agent-core — Shared contracts, storage, Eve materializer,
│   │   │                                       MCP config generator, provider clients
│   │   ├── src/
│   │   │   ├── common/types/                 — Cross-process type contracts (TASKS, agents, etc.)
│   │   │   ├── storage/                      — SQLite, migrations, secret vault
│   │   │   ├── providers/                    — ProviderClient abstraction
│   │   │   ├── eve/                          — Agent materializer, runtime manager
│   │   │   └── services/                     — FilesystemService, TodoService
│   │   └── package.json
│   └── mcp-servers/     @myboteam/mcp-servers — Bundled MCP server packages
│       ├── filesystem/
│       ├── gmail-mcp/
│       ├── calendar-mcp/
│       ├── complete-task/
│       └── ...
├── bundled-skills/                           — Shipped skill markdown files (read-only)
├── docs/                                     — Architecture docs, ADRs
├── scripts/                                  — Dev orchestrator, build helpers
├── pnpm-workspace.yaml                       — Monorepo config
├── tsconfig.base.json                        — Shared TS config
└── package.json
│
└── .local-data/ (runtime, see ADR-004)       — User data directory
    ├── myboteam.db                           — SQLite database
    ├── secure-storage.json                   — Encrypted secrets vault
    ├── agents/{slug}/                        — Eve generated agent files
    ├── skills/                               — User-created skills (from ADR-009 Skill Workshop)
    ├── standing-orders/                      — Persistent agent instructions (ADR-009)
    ├── notes/                                — Notes & todos storage reference
    └── artifacts/                            — User files written by agents
```

**Package Entry Points:**
- `@myboteam/agent-core` — daemon, web (core types, storage, providers)
- `@myboteam/agent-core/common` — web, desktop, daemon (shared type contracts)
- `@myboteam/agent-core/desktop-main` — desktop main process (DaemonClient, socket transport)

**Ownership Boundaries:**
| Layer | Owns | Does NOT Own |
|-------|------|-------------|
| apps/web | Routes, pages, renderer stores, components, i18n | Node.js, filesystem, daemon sockets, secrets |
| apps/desktop | Electron main, preload, OS bridges, packaging, updater | Agent domain logic, task execution, storage |
| apps/daemon | RPC routes, services, task execution, connectors | Renderer presentation, desktop packaging |
| packages/agent-core | Shared contracts, storage, providers, Eve config | Shell lifecycle, renderer components |
| packages/mcp-servers | Bundled MCP server packages | Token lifecycle (owned by daemon) |

### Consequences

#### Positive
- Clear ownership boundaries — no circular dependencies
- Independent build pipelines per app
- Shared types prevent contract drift across process boundaries
- MCP servers can be developed and tested independently
- Skills as markdown files are version-controlled and discoverable

#### Negative
- pnpm workspace overhead for dependency resolution
- Cross-package refactoring requires coordination
- Initial setup requires all packages to build correctly

#### Risks
- Risk: Package boundary violations (daemon importing web code) — mitigated by strict eslint rules and CI checks
- Risk: MCP server drift from agent-core types — mitigated by shared type package

### Common Alternatives

#### Option A: Single package (no monorepo)
**Description:** All code in one package with subdirectories.
**Trade-offs:** Simple but no enforced boundaries, can't independently build/test layers, one package.json for everything.

#### Option B: Two-package structure (desktop + agent-core)
**Description:** Desktop app as one package, everything else as agent-core.
**Trade-offs:** Simpler but daemon concerns mixed with core logic, harder to isolate tests.
