## ADR-004: Storage Architecture — better-sqlite3 + Encrypted Secrets Vault

### Status

**Accepted**

### Date

2026-06-24

### Owner

User/AI collaboration

### Sub-System

Data Layer

### Context

**Problem Statement:**
The application needs persistent storage for structured data (agents, tasks, conversations, settings) and secrets (API keys, OAuth tokens, connector credentials). All data stays on the user's machine — no cloud sync. The storage must survive process crashes and unexpected shutdowns.

**Forces:**
-Fast synchronous reads are important for the daemon's request-response cycle
- Secrets must never leave the machine, never appear in logs, and never enter the renderer process
- Migrations must be bidirectional and reversible for safe rollbacks
- The data directory must be portable — users should be able to backup or migrate their data
- App store packaging constraints: avoid native binary rebuild complexity where possible

### Decision

**Decision:**
Two-tier storage:

**Tier 1: better-sqlite3 (Synchronous SQLite)**
- WAL mode for concurrent read performance
- Tables: `agents`, `agent_runtime_files`, `skills`, `agent_skill_assignments`, `mcp_servers`, `agent_mcp_assignments`, `filesystem_access_rules`, `todo_projects`, `todos`, `conversations`, `messages`, `delegations`, `provider_settings`, `app_settings`, `tool_calls`, `debug_logs`
- Foreign keys enforced (`foreign_keys = ON`)
- Cascading deletes: conversation → messages cascade delete
- All migrations are bidirectional (up + down) and covered by tests
- Released migrations are immutable

**Tier 2: AES-256-GCM Encrypted Secrets Vault**
- File: `.local-data/secure-storage.json`
- Encryption: AES-256-GCM with PBKDF2 (100,000 iterations) key derivation
- Key material: platform + homedir + username + app identifier (with optional `MYBOTEAM_VAULT_KEY` env var override)
- Key prefix exposure only: the last 4 characters of the key are exposed to the UI for identification; full keys never leave the vault
- Atomic writes: write to temp file, then rename

**Data Directory:**
- Default: `~/.myboteam/` or `MYBOTEAM_DATA_DIR` env var
- Dev mode: `.local-data/` in project root
- Structure:
  ```
  .local-data/
  ├── myboteam.db           # SQLite database (WAL mode)
  ├── secure-storage.json   # Encrypted secrets
  ├── agents/{slug}/        # Eve generated agent files
  ├── artifacts/            # User files written by agents
  └── opencode/             # Generated opencode configs
  ```

**Key Architectural Rules:**
- Decrypted secrets NEVER enter the renderer process
- Decrypted secrets NEVER appear in logs, traces, screenshots, or test fixtures
- PID lock file prevents daemon multi-instance

### Consequences

#### Positive
- Synchronous SQLite reads are fast and predictable
- Encrypted vault provides strong protection for API keys
- Bidirectional migrations enable safe rollbacks
- Data directory is fully portable

#### Negative
- better-sqlite3 is a native binary — requires `@electron/rebuild` during packaging
- AES-256-GCM key derivation is CPU-intensive on first unlock
- Secrets decrypted in memory are vulnerable to memory inspection

#### Risks
- Risk: better-sqlite3 native binary fails to load in packaged app — mitigated by rebuild script and CI testing
- Risk: Vault key derivation fails on platform changes — mitigated by stable key derivation material (homedir + username)

### Common Alternatives

#### Option A: sql.js (WASM SQLite)
**Description:** SQLite compiled to WASM — zero native dependencies.
**Trade-offs:** No native rebuilds needed, simpler packaging, but slower synchronous performance and no direct WAL mode support.

#### Option B: JSON file storage
**Description:** All data stored as JSON files on disk.
**Trade-offs:** Simple to implement but no query capabilities, no relationships, no concurrent access, higher risk of corruption.
